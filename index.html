Testing the Penny beta, and what happens to your data

Download and test it

The beta runs on Penny's test server with a test bank. No real bank account is needed, and none should be used.

  1. On an iPhone running iOS 26 or later, install TestFlight.
  2. Open testflight.apple.com/join/zxSFk3yd on that iPhone, tap Accept, then Install. The app appears as Penny Dev.
  3. Tap Sign in or create account and create an account with your email. You'll get a code by email to confirm it.
  4. Set up Face ID, then link a bank. Pick any bank in Plaid's window and use Plaid's public sandbox login:
    Usernameuser_goodPasswordpass_goodCode, if asked1234
    These only work in the test environment and connect to sample data.
  5. Ask: "How much did I spend each day this week?", "Break down my spending by category" or "Which subscriptions am I paying for?"
  6. Optional: say "Hey Siri, talk to Penny Dev" to ask by voice.
  7. Send feedback from TestFlight → Penny Dev → Send Beta Feedback.

Your data and privacy, plainly

  • Kept in Canada. Everything Penny stores lives in its own AWS account in the Canada (Central) region, encrypted in transit and at rest.
  • No ads, no tracking, no selling. No advertising, analytics or tracking code.
  • Your bank password stays with Plaid. The link is read-only; Penny can't move money.
  • Short-lived chat. Encrypted on the phone, never backed up, and cleared after 30 minutes, on a new chat, or on sign-out. Server-side context is deleted after 30 minutes too.
  • How answers are written. Your question and the relevant figures go to Anthropic's Claude, processed in the United States. Card numbers, PINs and passwords typed into chat are blocked.
  • Retention. Account data is kept while the account is open; AI request logs for 1 year and server logs for 90 days. You can ask for deletion at any time.

Full details are in the MeetPenny app privacy policy. Penny explains your own spending. It isn't financial, tax or legal advice, and it's for people 18 and older.

01 / Fintech AI assistant

Answers that appear as they're written, without a single data race.

Senior iOS Engineer (contract) · Publicis Sapient · Mar 2026 – Aug 2026 · Toronto, hybrid

A wealth-management firm was adding a generative-AI investing assistant to its flagship iOS app. Answers had to stream in token by token, like a consumer chat app, but they also had to render tables, lists and charts, in a financial app where a half-drawn table is worse than none.

Constraints

  • Correctness over flair. A chart with an out-of-range value or a table with a missing column can't reach an investor's screen.
  • A moving schema. The backend could start sending new response types before the app knew about them.
  • iOS 17 minimum. That ruled out newer TipKit features for onboarding.
  • A mixed host app. The assistant had to launch from both SwiftUI and legacy UIKit screens.
  • Staged rollout. Phase 1 went to a small slice of customers first, so everything needed to be observable and reversible.

Options I weighed

  • RejectedWait for the whole response, then render. Simplest to build, but users would stare at a spinner for the length of a full generation.
  • RejectedServer-Sent Events with a generic client. Event framing alone doesn't tell the client what kind of UI component it's receiving, so typed rendering would still need a second layer.
  • ChosenNewline-delimited JSON over an HTTP data stream, parsed by a custom tokenizer. Each line is a complete, typed component, so a table arrives and renders as one unit instead of being guessed from partial markdown.

The design

  1. Alamofire DataStreamRequestRaw bytes from the backend-for-frontend, as they arrive.
  2. actor JSONLTokenizerAccumulates a buffer, splits on newlines, extracts only complete objects.actor isolation: no shared mutable buffer
  3. Decode on a component discriminatorEight types, validated at the parse boundary (table header/row parity, chart value bounds). Unknown types degrade gracefully instead of crashing.
  4. Orchestration service · custom @globalActorSession lifecycle, chunk-by-chunk message assembly, handoff from loading state to first chunk, cancel and retry.
  5. ChatViewModel · @MainActorUI state is only touched on the main actor; everything crossing the boundary is Sendable.
  6. SwiftUI chat package50+ files covering messages, markdown, tables, lists, charts, typing and retry. Later reused for live-agent chat.
Wire valueRenders as
chat-responseMarkdown text bubble
tablePlain table grid
ordered-list / unordered-listNumbered or bullet list
line-chart / bar-chart / pie-chartChart views with their own ViewModels
suggested-user-intentsSuggestion pills

The data races were the real problem. The first version processed chunks off a callback queue, and races surfaced under load. Moving the tokenizer into an actor, serializing stream processing on a custom global actor, enforcing @MainActor at the UI boundary and making every crossing type Sendable eliminated them.

  • Contract first. I co-designed the streaming schema with the backend and AI-platform teams, then aligned iOS, backend and design on it.
  • Testable by construction. Eight SPM packages, with a protocol and a paired mock for every ViewModel. The tokenizer, decoding and ViewModels are covered with XCTest and Swift Testing.
  • Coach marks without iOS 18. A 17-file TipKit-style framework back-deployed to iOS 17, adopted by other engineers and validated through iOS 26.
  • Claude in the loop. Custom Claude commands run a first-pass review against the team's Swift/SwiftUI guidelines before a human looks.

Outcome

Phase 1Shipped to production on a staged rollout
0Data races under load after the actor redesign
17 → 26iOS range the coach-mark framework supports

What I'd do differently

Put an explicit schema version in the stream from day one. Graceful degradation keeps the app from breaking, but it also hides when the client has fallen behind the backend.

02 / TruPOS payments

Field sales kept taking payments with no signal.

Lead iOS Engineer · Tech Mahindra · Dec 2024 – Mar 2026

The client needed one iOS app to be the checkout hub for several business lines. Its users are field sales staff taking card payments at customer sites, often in basements, rural properties and other places with weak or no signal. Every payment that failed there was lost revenue and an awkward moment with a customer.

Constraints

  • Unreliable connectivity is the normal case, not an edge case.
  • Hardware in the loop. Bluetooth card readers and MFi accessories had to keep working with the app in the background.
  • Shared logic. Several internal apps needed the same payment, receipt and deep-link behaviour.
  • Integrations. External tools such as Field Service 365 launch into checkout through universal links and URL schemes.

Options I weighed

  • RejectedBlock checkout while offline. Easiest to reason about, but it fails exactly the people the app exists for.
  • RejectedHold failed requests in memory and retry. The app can be killed or the phone restarted long before signal returns, and the payment would be lost silently.
  • ChosenA durable queue in Core Data, drained by background tasks, with a 72-hour retention window. Payments survive app termination and sync on reconnect. 72 hours covers a field team's longest realistic stretch without signal.

The design

  1. Checkout · SwiftUI + MVVMDynamic, form-based screens for checkout, history and merchant onboarding.
  2. PaymentServiceBluetooth card reader with background modes and a retry layer for flaky accessory connections.
  3. OnlineSubmit to API, then poll status live (Combine + URLSession) and update the UI as it settles.
    OfflineWrite to the Core Data queue: status, attempt count, created-at (≤ 72h).
  4. BGTaskScheduler + reconnect triggerDrains the queue with retries and marks each payment synced.client-generated transaction ID, so a retry can't charge twice
  5. Shared Swift packagePayments, receipts and deep linking, used by three internal apps.
  • Release engineering. I owned CI/CD and automated TestFlight and App Store delivery with Fastlane, GitHub Actions and Xcode Cloud, replacing a manual process.
  • Performance. Instruments traces found retain cycles and redundant work in the checkout path. Fixing them improved cold start and memory pressure.
  • Quality. 80% unit-test coverage on business logic.

Outcome

≈0Offline transaction failures
3 appsOn one payments package, with no more per-app rewrites
20–50%Shorter release cycles after automation

What I'd do differently

Show the queue to the user sooner: something like "3 payments waiting to sync" on the home screen. Trust in an offline system comes from seeing it work.

03 / Dr Godly

Clinical AI that never sends a patient's voice to a server.

Founder & Lead Engineer · Jan 2024 – present · limited production pilot with early customers

Doctors lose consultation time to note-writing. An assistant that transcribes and summarizes helps, but in healthcare, sending patient audio to a third-party model creates privacy and trust problems. I wanted to know whether the whole loop could stay on the phone.

Constraints

  • Privacy as a hard rule. Patient audio and transcripts never reach a server for AI processing.
  • Clinical vocabulary. General-purpose models handle drug names and clinical shorthand poorly.
  • Real time. Transcription has to keep up with a live video call between two people.
  • One engineer. The iOS client, Android companion, shared package and backend are all built by me.

Options I weighed

  • RejectedA cloud LLM for transcription and summaries. Fastest to build, and the approach I'd used in earlier telehealth work. Rejected because patient audio would leave the device, which is a hard sell to clinics.
  • RejectedThe base on-device model alone. Private, but it stumbled on clinical terms and note structure.
  • ChosenApple Foundation Models with a LoRA adapter tuned for clinical vocabulary and note summarization, with default safety guardrails. Private by design, and good enough at the domain.

The design

  1. Twilio Video consultationDoctor and patient on a secure call.
  2. Apple Speech · doctorReal-time speech-to-text
    Apple Speech · patientReal-time speech-to-text
  3. Speaker-tagged transcriptAssembled and kept on the device.
  4. Foundation Model + clinical LoRA adapterNote summary on device, plus text-to-speech playback.no patient audio or transcript leaves the phone
  5. Node.js backend · Google App EngineAuth and sessions. It coordinates the workflow but never receives patient audio or transcripts.

Outcome

100%AI processing on device
6+ reposiOS, Android, shared Swift package, backend, built solo
PilotLimited production use with early customers

What I'd do differently

Build a scored evaluation set of consented, de-identified clinical phrases before the first fine-tune, so every adapter version is measured rather than judged by feel.

04 / NEOM Smart City

One framework under ~20 apps, so no team rebuilt networking or auth.

Senior / Lead iOS Engineer · NEOM via Tech Mahindra · Jun 2023 – Jan 2024 · Saudi Arabia

NEOM was building many apps for residents, visitors and service providers at once. Without a shared foundation, every team would have built its own networking, auth and security, each slightly different and each patched separately.

Constraints

  • One security baseline. OAuth and SSL pinning had to behave identically in every app.
  • Many consumers. A breaking change would hit about 20 apps at once.
  • GraphQL backends. Clients needed type safety, not hand-written query strings.

Options I weighed

  • RejectedA template project copied per app. Fast on day one, but security fixes drift as soon as the copies diverge.
  • RejectedA CocoaPods or binary framework. I'd used CocoaPods for TD's foundation framework. Here, SPM's first-party Xcode support and source visibility won.
  • ChosenA Swift package with explicit interface contracts and a versioning strategy, so teams could upgrade on their own schedule.

The design

  1. Core framework · SPM, versionedNetworking · OAuth 2.0 · SSL pinning · Apollo iOS for type-safe GraphQL · shared UI
  2. Adopting apps
    Smart City appapp 2app 3…~20 apps
  3. Smart City app featuresIn-app assistant for utilities, transport and support (OpenAI client with LangChain-based prompts), Twilio audio and video for resident-to-agent support, and Apple Speech for voice.
  • Design reviews with product, backend and security, where I owned the architectural decisions.
  • People. I mentored three engineers and led a small iOS team through the full lifecycle to launch.

Outcome

~20Internal apps adopted the core framework
v1The Smart City app's first App Store release
3Engineers mentored to launch

What I'd do differently

Ship a small sample app alongside the framework from week one. Getting 20 teams to adopt something is mostly a documentation problem.

05 / Kroger

The release pipeline the whole iOS org shipped with.

Senior / Lead iOS & Release Engineer · Kroger via Tech Mahindra · Jan 2023 – Jun 2023

Kroger runs a family of grocery banners (Kroger, Ralphs, Fred Meyer, Harris Teeter), and each is a separate App Store app with its own signing and release. I was also delivering a new customer-facing feature, Gamification, to all of them.

Constraints

  • Multiplication. Four apps × signing identities × dev and production environments.
  • Full customer base. Gamification v1.0 and v2.0 went to everyone, so rollouts had to be measurable and reversible.

Options I weighed

  • RejectedManual Xcode archives per banner. Slow, and one wrong signing identity costs a release day.
  • RejectedSeparate scripts per banner. Duplicated logic that drifts with each new banner.
  • ChosenOne parameterized pipeline: Fastlane, GitHub Actions, shell, Ruby and Node.js, adopted by the entire iOS org across all four banner apps.

The design

  1. Pull request → GitHub ActionsEvery change goes through the same path.
  2. Fastlane lane (banner, environment)
    krogerralphsfred meyerharris teeterdev | prod
  3. Build → sign → deliverPer-banner identity, then TestFlight or the App Store.
  4. Feature flags + experimentsFirebase Remote Config flags and A/B tests gate the Gamification rollout.
  5. MonitorCrashlytics and Grafana, watched during each rollout.

Outcome

4Banner apps on one pipeline
Org-wideThe pipeline was adopted by the entire iOS org
v1 → v2Gamification shipped to the full customer base

What I'd do differently

Add automated screenshot diffs per banner. Most multi-brand bugs are visual, like the wrong logo or colour, and only humans were catching them.
